# Phase 2 Summary Report: CISSP Risk Management & Incident Response Expansion

## Executive Summary

Phase 2 expands the original Elastic SIEM lab into a CISSP-aligned Security Operations, Risk Management, and Incident Response project.

The original lab focused on building the Elastic Stack environment, ingesting logs, creating dashboards, and simulating attacks. Phase 2 builds on that foundation by adding a Windows Enterprise VM as a new monitored endpoint and using the SIEM to support authentication monitoring, network telemetry review, incident response documentation, risk management, governance, and CISSP domain mapping.

This phase demonstrates how technical monitoring supports security governance and operational decision-making.

---

## What Changed from Phase 1

| Phase | Focus | Summary |
|---|---|---|
| Phase 1 | Elastic SIEM Build | Built the Elastic SIEM lab, configured ingestion, and created initial visibility into lab activity |
| Phase 2 | CISSP Risk & Incident Response Expansion | Added Windows endpoint monitoring, incident response playbooks, risk register, governance policy, evidence index, and CISSP control mapping |

Phase 2 does not repeat the original SIEM installation. It uses the existing SIEM lab as a foundation for higher-level security operations and risk management work.

## Security Activities Performed

### 1. Windows Endpoint Enrollment

The Windows Enterprise VM was enrolled into Elastic Fleet using Elastic Agent. This created centralized endpoint visibility and allowed Windows telemetry to be reviewed in Kibana.

Related evidence:

- [Windows Agent Healthy PowerShell](screenshots/windows-agent-powershell-healthy.png)
- [Fleet Windows Agent Healthy](screenshots/fleet-windows-agent-healthy.png)

---

### 2. Failed Logon Detection

Failed Windows logons were generated by entering the wrong password on the Windows Enterprise VM. The resulting Event ID 4625 logs were located in Kibana Discover.

Query example:

```text
host.os.type: "windows" AND event.code: 4625
```

Related evidence:

- [Failed Logon 4625](screenshots/phase-2-windows-failed-logon-4625-discover.png)
- [Brute Force Playbook](incident-response/brute-force-incident-playbook.md)

---

### 3. Successful Logon Monitoring

Successful Windows logons were reviewed using Event ID 4624. This supports account activity monitoring and helps determine whether failed logon activity was followed by successful access.

Query example:

```text
host.os.type: "windows" AND event.code: 4624
```

Related evidence:

- [Successful Logon 4624](screenshots/phase-2-windows-successful-logon-4624-discover.png)
- [Brute Force Playbook](incident-response/brute-force-incident-playbook.md)

---

### 4. Nmap-Related Network Telemetry Review

Nmap-related testing was performed from Kali against the Windows Enterprise VM. Kibana Discover was used to review Windows endpoint network telemetry associated with the Kali source IP.

Query example:

```text
event.category: network AND source.ip: "192.168.70.130"
```

Related evidence:

- [Nmap-Related Network Events](screenshots/phase-2-nmap-related-windows-network-events.png)
- [Nmap Scan Playbook](incident-response/nmap-scan-incident-playbook.md)

This testing identified a visibility gap: not every scan probe appeared as a separate event in Discover. This finding supports the recommendation to enable additional firewall or network-flow logging.

---

### 5. Agent Health Monitoring

During testing, the Windows Elastic Agent stopped and had to be restarted. This was documented as an operational risk because endpoint visibility depends on agent health.

Related evidence:

## Risks and Findings

Key risks identified during Phase 2 include:

1. Failed Windows logon activity may indicate brute force attempts.
2. Failed logons followed by successful logons may indicate credential compromise.
3. Network reconnaissance may expose open services such as RDP.
4. Limited scan visibility may reduce detection coverage.
5. Elastic Agent failure can interrupt endpoint monitoring.
6. Weak authentication controls can increase access risk.

These findings are documented in the [Risk Register](risk-management/risk-register.md).

---

## Lessons Learned

- A Windows endpoint greatly improves the realism of the SIEM lab.
- Failed logon events alone are not enough; successful logons must also be reviewed.
- Agent health is critical because stopped agents create monitoring blind spots.
- Nmap activity may not always appear clearly as Nmap in Discover; correlation with source IP, time, and endpoint telemetry is required.
- Visibility gaps should be documented as risks and used to improve logging controls.
- Evidence screenshots make the project stronger for portfolio review and CISSP CPE support.
